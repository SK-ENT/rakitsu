Messaging between sessions

One live session can send a message into another. The target must have opted in, the message starts a normal turn there, and a pair of sessions cannot ping-pong forever.

The playground is a simulation of deliverMessage and handleSessionMessage in internal/server/session_message.go (same order of checks, same status names and HTTP codes). The recording at the bottom is a real run against a local serve, and the playground can replay its main cases.

Rules in order




    

  1. Auth: if the server has RAKITSU_API_TOKEN (or RAKITSU_SESSION_MSG_TOKEN) set, the request needs that bearer token, else 401.
    2. 

  2. Body: text is required (400) and at most 16 KiB (413). With wait, timeout_ms defaults to 30000 and is clamped to 120000.
    3. 

  3. Rate limit: at most 6 tries per 30 seconds between the same pair of sessions, counted before any other check (429). Busy and refused tries count too.
    4. 

  4. Target lookup: unknown id gives 404 (or "mailboxed" for a known external mailbox).
    5. 

  5. Opt-in: the target config needs settings.session_msg.enabled: true, else rejected (403).
    6. 

  6. Queue: a running turn is never interrupted. One message may wait behind it; if that slot is taken the answer is busy (409).
    7. 

  7. With wait the server blocks for the turn and returns the reply; if the wait runs out it answers waited: false and the turn still finishes in the background.
    8. 



from_name and from_session_id are claimed by the sender and not verified. In the receiving transcript the message is shown as coming from another session. Agents get the same ability through the send_message and list_sessions tools. See the bridge doc and reference pages.
